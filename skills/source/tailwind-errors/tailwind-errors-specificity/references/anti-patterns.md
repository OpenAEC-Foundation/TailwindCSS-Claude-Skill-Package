# tailwind-errors-specificity : Anti-Patterns

The traps that produce cascade and specificity failures.

## Anti-Pattern 1 : Custom CSS Outside Any @layer

### Symptom

Custom classes override Tailwind utilities. Padding, color, border
unexpectedly fixed to your custom rule. No `!important` involved.

### Wrong

```css
@import "tailwindcss";

.card {
  padding: 1rem;
  background: white;
}
```

### Right

```css
@import "tailwindcss";

@layer components {
  .card {
    padding: 1rem;
    background: white;
  }
}
```

### Root cause

Native CSS `@layer` puts UNLAYERED rules at the top of the cascade
(except inline style and `!important`). Wrapping custom rules in
`@layer components` lets `@layer utilities` (Tailwind utilities) win
naturally. ALWAYS layer your custom CSS.

## Anti-Pattern 2 : Mixing v3 and v4 !-modifier syntax

### Symptom

`!font-bold` works on some pages, `font-bold!` works on others. Or
neither works after upgrade.

### Wrong (v4 project)

```html
<div class="!font-bold">
```

### Right (v4 project)

```html
<div class="font-bold!">
```

### Root cause

v3 expects `!` BEFORE the utility. v4 expects `!` AFTER. The other
syntax is treated as an unknown class and emits NO CSS. Pick ONE
version and align all markup with its syntax. The official codemod
(`npx @tailwindcss/upgrade@next`) handles this.

## Anti-Pattern 3 : Expecting @apply to keep !important (v3)

### Symptom

```css
.btn-danger {
  @apply !bg-red-500;
}
```

The element shows red background but does NOT win over `:hover` rules
or third-party overrides. Inspection shows NO `!important` flag.

### Wrong (v3)

```css
.btn-danger { @apply !bg-red-500; }
```

### Right (v3)

```css
.btn-danger { @apply bg-red-500 !important; }
```

### Right (v4)

```css
.btn-danger { @apply bg-red-500!; }
```

### Root cause

v3 INTENTIONALLY strips `!important` flags from utilities pulled in
via `@apply`, "to avoid specificity conflicts" per docs. To preserve
the flag in v3, append `!important` at the end of the declaration.
v4 changed this behaviour and preserves `!`-suffix through `@apply`.

## Anti-Pattern 4 : Same-property duplicate inside @apply

### Symptom

```css
.btn {
  @apply px-4 py-2 px-8;   /* px-4 silently dropped */
}
```

Developer expects all three to coexist. Layout uses px-8 only.

### Right

```css
.btn {
  @apply py-2 px-8;        /* clear about intent */
}
```

### Root cause

`@apply` inlines utilities by declaration order. Two utilities
targeting the SAME property (`padding-left`/`padding-right` here)
produce duplicate CSS declarations ; the LAST one wins. There is no
mechanism to "merge" or "add" padding values. ALWAYS keep one utility
per CSS property in any @apply line.

## Anti-Pattern 5 : Two-class selector wrapping a utility

### Symptom

```css
.card .p-4 { padding: 2rem; }
```

Developer wrote this to "override p-4 inside cards". But now p-4
NEVER applies its 1rem padding inside a card.

### Right

```css
/* Use a different utility */
.card { @apply p-8; }    /* card itself has padding-8 */
```

### Root cause

The descendant combinator increases specificity to 0,0,2,0, beating
Tailwind's 0,0,1,0 single-class utilities. This DEFEATS the entire
utility-first model. ALWAYS keep utilities as single-class selectors.
If you need a card-specific padding, apply it as a utility on the
card element OR via `@layer components` rule on `.card`.

## Anti-Pattern 6 : Plugins in wrong order

### Symptom

A plugin you wrote to override `@tailwindcss/typography` defaults
sometimes wins, sometimes loses, depending on which build ran last.

### Wrong

```js
plugins: [
  require("./my-typography-overrides"),     // FIRST -> low priority
  require("@tailwindcss/typography"),       // LAST -> wins
],
```

### Right

```js
plugins: [
  require("@tailwindcss/typography"),       // FIRST -> low priority
  require("./my-typography-overrides"),     // LAST -> wins
],
```

### Root cause

Plugins emit into the SAME layer. Within a layer, source order
decides cascade. LATER plugin = LATER CSS = WINNER. ALWAYS list
plugins from least-specific to most-specific.

## Anti-Pattern 7 : Custom utility outside @utility/@layer utilities

### Symptom

```css
.tab-4 { tab-size: 4; }   /* unlayered */
```

Class works for static use but `hover:tab-4` and `md:tab-4` do not.

### Right (v4)

```css
@utility tab-4 {
  tab-size: 4;
}
```

### Right (v3)

```css
@layer utilities {
  .tab-4 { tab-size: 4; }
}
```

### Root cause

Variants (hover:, md:, dark:) are generated by Tailwind for classes
that exist IN ITS UTILITY REGISTRY. Unlayered classes are unknown to
Tailwind ; no variants get generated. ALWAYS declare custom utilities
via `@utility` (v4) or `@layer utilities` (v3).

## Anti-Pattern 8 : Relying on inline style to "override Tailwind"

### Symptom

```jsx
<div style={{ padding: 10 }} className="p-8">
```

Developer says "I'll just use inline style to override the utility".
Code base grows full of inline styles. Tailwind's value is undermined.

### Right

Pick ONE approach :

- Use Tailwind for layout / theming -> drop inline style.
- Use Tailwind for utilities AND need a one-off value not in theme
  -> use arbitrary value : `className="p-[10px]"`.
- Use a `!`-modifier when third-party CSS forces it.

### Root cause

Inline style has 1,0,0,0 specificity and CANNOT be overridden by
classes (without `!important`). Mixing inline styles and utilities
defeats the utility-first model and creates two parallel styling
languages in the codebase.

## Anti-Pattern 9 : @apply inside scoped style without @reference (v4)

### Symptom

```
Error: Cannot apply unknown utility class: text-2xl
```

Or scoped CSS compiles with NO styles applied to elements.

### Wrong

```vue
<style scoped>
  h1 { @apply text-2xl font-bold; }
</style>
```

### Right

```vue
<style scoped>
  @reference "../app.css";
  h1 { @apply text-2xl font-bold; }
</style>
```

### Root cause

Vue/Svelte/MDX scoped styles process in isolation. No theme. No
utility registry. `@apply` cannot resolve. `@reference` imports the
context (NOT the CSS output ; output stays in the main bundle).

## Anti-Pattern 10 : Sprinkling ! everywhere instead of fixing root cause

### Symptom

Every override uses `!`-modifier. Markup full of `bg-red-500!
font-bold! p-4! text-white!`. Cascade is broken everywhere.

### Wrong

```html
<button class="bg-blue-500! text-white! px-4! py-2! rounded-md!">
```

### Right

Diagnose WHY plain `bg-blue-500` does not apply. Common causes :

- Unlayered custom CSS (fix : move to @layer components)
- Higher-specificity selector somewhere (fix : avoid the selector)
- Third-party CSS loaded after Tailwind (fix : layer it OR re-order)

The `!`-modifier should be a LAST resort, not a default. Use it only
when you cannot edit the conflicting CSS (e.g. minified vendor
bundle).

## Anti-Pattern 11 : Forgetting @layer when porting v3 to v4

### Symptom

After v4 upgrade, custom CSS that previously worked now wins over
utilities.

### Wrong (v3 to v4 unchanged)

```css
/* worked in v3 with @tailwind directives */
@tailwind base;
@tailwind components;
@tailwind utilities;

.btn { padding: 0.5rem 1rem; }   /* not @layer'd but v3 was lenient */
```

In v4 after replacing with `@import "tailwindcss"`, the unlayered
`.btn` now WINS over utilities.

### Right (v4)

```css
@import "tailwindcss";

@layer components {
  .btn { padding: 0.5rem 1rem; }
}
```

### Root cause

v4's stricter @layer enforcement exposed unlayered CSS that worked
"by accident" in v3. The migration codemod does NOT auto-wrap your
custom CSS in @layer. ALWAYS audit after migration.

## Anti-Pattern 12 : Two utilities, both with !-modifier

### Symptom

```html
<div class="bg-red-500! bg-blue-500!">
```

Result is unpredictable (whichever appears later in compiled CSS).

### Right

Pick ONE.

### Root cause

Both classes generate `!important`. Browser cascade for same-specificity
+ same-important rules falls back to source order. Tailwind's CSS
output order is deterministic but not always obvious.

## Anti-Pattern 13 : Plugin emits class in wrong layer

### Symptom

Your custom plugin emits a class that you expected to be a UTILITY
(overrides components) but it's emitting into COMPONENTS (gets
overridden by other utilities).

### Wrong (v3 plugin)

```js
plugin(function ({ addComponents }) {
  addComponents({
    ".btn-glow": { boxShadow: "0 0 8px rgba(0,0,255,0.5)" },
  });
});
```

### Right

```js
plugin(function ({ addUtilities }) {
  addUtilities({
    ".btn-glow": { boxShadow: "0 0 8px rgba(0,0,255,0.5)" },
  });
});
```

### Root cause

`addComponents` -> emits into `@layer components`. `addUtilities` ->
emits into `@layer utilities`. Components LOSE to utilities. If you
want utility-level priority for a custom class, use `addUtilities`
(v3) or `@utility` (v4).

## Anti-Pattern 14 : Confusing important: config flag with !-modifier

### Symptom

```js
// v3 tailwind.config.js
module.exports = {
  important: true,   // makes ALL utilities !important
};
```

Suddenly EVERY utility is `!important`. Cascade becomes unmanageable.
Custom CSS in @layer components is impossible to override.

### Right

Use important: ONLY in specific contexts :

```js
important: "#app",   // wraps all utility selectors with #app
```

This INCREASES specificity to 0,1,1,0 without `!important`. Useful
when embedding Tailwind into a host page that already has CSS.

### Root cause

Global `important: true` is a nuclear option. Per-class `!`-modifier
is surgical. ALWAYS prefer per-class. Reserve `important: "#scope"`
for embedding-into-host scenarios.

v4 has NO global important flag. Use per-class `!`-suffix.

## Anti-Pattern 15 : Adding @layer to legacy CSS file you do not control

### Symptom

You import a vendor CSS file (`bootstrap.css`, `mui-base.css`) into
your @layer base block. Some of its rules use `!important`. Others
use `*` selectors. Cascade goes wild.

### Wrong (naive)

```css
@layer base {
  @import "bootstrap/dist/css/bootstrap.css";
}
```

### Right

Either layer it AND test thoroughly, OR keep it unlayered AND
override individual rules with Tailwind's `!`-modifier on key
elements.

### Root cause

Wrapping unfamiliar CSS in `@layer` changes the cascade for EVERY rule
in the file. Vendor CSS often uses tricks (universal selectors,
`!important`, specificity hacks) that interact unpredictably with
@layer. ALWAYS audit before layering vendor code.
